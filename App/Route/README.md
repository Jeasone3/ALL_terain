# 小车运动与路线使用说明

`Route` 决定下一步做什么，`ModeFSM` 执行动作。TIM4 每 10 ms 只调用一次
`ModeFSM_Tick()`，流程是灰度采样 → 项目接管判断 → 默认 Route 决策 → 当前模式 PID → 电机。
主循环不重复调用 `ModeFSM_Tick()`，不直接修改 `g_mode_fsm`。

## 两个模式

| 模式 | 电机反馈来源 | 灰度检测 | IMU 采样与解算 |
|---|---|---|---|
| `MODE_TRACK` | 循迹 PID | 运行，用于跟线和条件判断 | 暂停 |
| `MODE_IMU` | IMU 角度 PID | 运行，只用于条件判断 | 运行 |

IMU 子状态是 `IMU_TURN_LEFT`、`IMU_TURN_RIGHT`、`IMU_FORWARD`。
停车和故障由 `status` 表示，不增加第三个运动模式。

## 动作接口

```c
#include "Mode_FSM.h"
#include "Route.h"

/* 自己决定所有动作时，先关闭内置的示例路线。 */
Route_Enable(0);
Car_Track();                      // 自动跟线，持续到下一动作
Car_ImuForward();                 // 以接受动作时的方向为 0°，持续保持航向
Car_TurnLeft90(MODE_TRACK);       // 原地左转 90°，完成后自动接循迹
Car_TurnRight90(MODE_IMU);        // 原地右转 90°，完成后自动接 IMU 直行
Car_Stop();                       // 下一个控制帧停车
```

上面的调用是接口清单，实际每次只选择一个动作。`Car_*` 只提交请求，最多等待一个
10 ms 控制帧生效；同帧普通请求最后一个生效，停车优先。不要在主循环或周期函数中
反复提交同一个运动请求，否则会不断重建角度基准并清 PID 历史。

左转目标为 `+90°`，右转为 `-90°`，均相对于本次动作起点。直接发起转弯不包含
转前前移。转完接 `MODE_IMU` 时保留原来的转弯目标；如果再单独调用
`Car_ImuForward()`，则建立新的零度基准，保持接受该指令时的朝向。

## 当前示例路线

`ModeFSM_Init()` 同时初始化 Route，默认开启示例决策，保留当前测试的方向策略：

| 条件 | 上层安排的步骤 |
|---|---|
| 左侧四路连续三帧在线 | IMU 直行 80 帧 → 左转 90° → 循迹 |
| 右侧四路连续三帧在线 | IMU 直行 80 帧 → 右转 90° → 循迹 |
| 八路连续两帧在线，且未被项目接管 | 项目阶段加一，保持巡线，不提交 IMU 直行请求 |

方向策略集中在 `Route.c` 的 `select_route_action()`，以后在这里查询规划路线，
选择左、右或直行。前移是独立的 `ROUTE_APPROACH` 步骤，不藏在转弯控制中。
左右路口的默认前移 80 帧约 **800 ms**，需要按车速和几何尺寸校准。
IMU 控制航向，没有编码器时不能把固定时间当作精确距离。

十字由 `junction_event` 驱动阶段推进：未离开同一路口时只加一次；连续三帧无路口
解除锁存后，下一新十字才允许再次计数。关闭默认决策、停车、外部请求优先帧以及
其他动作执行期间不计数。原 `ROUTE_CROSSING` 保留为备用状态，默认十字不再进入它。

外部 `Car_*` 请求会取消未完成的示例路线步骤，当帧不会被 Route 覆盖。
后续新路口仍可能触发默认策略；手动测试或由另一个上层模块接管时使用 `Route_Enable(0)`。
`enabled` 为 0 时跳过默认路线步骤，`PathPlan_Tick()` 位于开关判断之前，
你的代码仍会继续检查条件；项目动作与结束方式由你自行编写。
关闭自动 Route 不会停止已经执行的动作，结束运动请另发 `Car_Stop()` 或新动作。

## 你自己写项目动作

`g_project_stage` 记录地图阶段，你的项目代码写在 `Route.c` 的 `PathPlan_Tick()`。
当前项目 1、2 均采用独立函数和非阻塞计时；项目 2 在项目 1 正常完成后的下一新十字执行十秒 IMU 直行。

| 代码 | 用途 |
|---|---|
| `g_project_stage` | 默认从 0 开始，自动决策确认新十字时加一；项目内按需要自行修改 |
| `Route_Enable(0u)` | 关闭默认自动决策，当前动作和你的规划函数继续运行 |
| `Route_Enable(1u)` | 开启默认自动决策，不会单独把运动切回巡线 |
| `PathPlan_Tick()` | 你的项目代码写在这里，每 10 ms 检查一次自己的条件 |

原来的通用项目步骤枚举和固定三秒直行后左转流程均已移除。
项目之间默认巡线、左右路口角度转弯、新十字计数仍由 Route 完成。
`main.c` 的上电 IMU 直行测试保持关闭。

### 项目 1：IMU 直行十秒

触发条件为自动决策开启、正常巡线且处于 `ROUTE_FOLLOW`，阶段为 1，
本帧确认一个新十字。计数在规划函数之前，因此从阶段 0 启动时，
首个新十字先把阶段加到 1，再在同一控制帧执行项目 1 的入口。

进入时关闭自动决策、打开蜂鸣器，并只提交一次 `Car_ImuForward()`。
此函数随即返回，让运动状态机继续每 10 ms 更新 IMU、PID 和电机。
后续帧不要求十字事件持续存在：`state_frames >= 10u` 时关闭蜂鸣器，
`state_frames >= 1000u` 时提交一次 `Car_Track()` 并开启自动决策。
蜂鸣提示与十秒直行同时计时；要修改时间，分别修改这两个帧数。

项目 1 不修改地图阶段，完成标志防止在同一阶段再次接管。
后续新十字可以由默认决策继续推进阶段。外部换动作、停车或故障会取消本次项目，
关闭提示音，并保留自动开关；不会再自行恢复运动。`Route_Init()` 清除项目运行标志。

### 项目 2：下一新十字后 IMU 直行十秒

项目 1 正常完成后，先恢复巡线和默认自动决策；等待下一新十字连续两帧确认。
Route 在同一帧把阶段从 1 加到 2，`PathPlan_Tick()` 再调用 `Project2()`。
入口要求项目 1 正常完成、项目 2 尚未结束、自动决策开启、正常巡线且处于 `ROUTE_FOLLOW`，
同时满足阶段 2 和本帧新十字事件。项目 1 被停车、外部动作或故障中断时，不会启动项目 2。

`Project2()` 沿用项目 1 的写法：首次调用关闭默认决策，只提交一次 `Car_ImuForward()` 并立即返回；
后续帧继续检测灰度、更新 IMU 和运行角度 PID，以 `g_mode_fsm.state_frames` 非阻塞计时。
达到 `1000u` 帧（约 10 秒）后，只提交一次 `Car_Track()` 并调用 `Route_Enable(1u)` 恢复自动决策。
项目 2 不增加蜂鸣提示；日志入口为 `PROJ2_FWD`，完成为 `PROJ2_DONE`。

同一十字未离开时不会重启项目。运行期间的新路口只更新检测值，不推进阶段；完成时阶段仍为 2，
后续自动巡线确认下一新十字才加到 3。外部动作、停车或故障取消项目 2 后，保持自动决策关闭，
不会到原定结束时间再抢回控制。`Route_Init()` 会清除两个项目的运行和结束标志。

### 自己选择动作

例如你要在阶段 3 开始一个右转项目，可以在 `PathPlan_Tick()` 里参考下面的入口。
这只是写法示例，没有启用到固件中：

```c
if (g_project_stage == 3u && g_route.enabled) {
    Route_Enable(0u);                  /* 先关闭默认决策。 */
    Car_TurnRight90(MODE_TRACK);       /* 本次动作由你选择，也可以换成其他 Car_*。 */
    return;
}
```

开关被关掉后，这个入口不会每帧重复发送右转。右转完成后运动层按参数接巡线，
默认路线仍保持关闭；什么时候开启由你自己的完成条件决定。
需要 IMU 直行、左转、停车时分别使用 `Car_ImuForward()`、`Car_TurnLeft90()`、
`Car_Stop()`，每次转换只提交一个动作。

### 自己决定何时结束

在你确认完成的分支中，自己选择后续阶段和运动，例如：

```c
g_project_stage = 4u; /* 是否改变阶段、改成多少，由你的地图条件决定。 */
Car_Track();         /* 想恢复自动巡线时，先选择巡线动作。 */
Route_Enable(1u);
```

若进入项目的条件是阶段 3，结束后应改变阶段或使用你自己的标志，避免重新进入。
恢复开关的这一帧先接受你提交的动作，下一帧才恢复默认决策。
不要在同一次规划调用中先关闭又立即开启开关，再期待执行一串连续动作。

`Car_*` 是单槽请求，不是动作队列。先直行、后转弯这类过程由你自己的条件分帧安排；
直行计时可看 `g_mode_fsm.state_frames`，转弯成功可比较开始前后的 `turn_count`。
不需要使用统一的项目步骤枚举，也不要在这个 10 ms 入口里使用 `HAL_Delay()`。

### 阶段和调用顺序

正常自动巡线时，新十字计数在你的规划函数之前执行：从阶段 0 开始，
首个新十字同帧读到阶段 1 和新事件；项目完成并恢复自动巡线后，
下一个新十字同帧读到阶段 2 和新事件。可以直接用阶段值和十字事件组合判断。
自动关闭、停车、故障、外部请求优先帧及 IMU/路线动作执行期间不计数。

关闭自动功能或主动停车时，你的规划入口仍会运行；外部动作优先帧、空输入和
运动故障时跳过，不自动覆盖人工动作或恢复故障。停车后是否提交新动作由你决定。
写入阶段集中在此 TIM4 入口或启动 TIM4 前，前台只读取这个 32 位变量，
不要由主循环和中断同时对阶段执行加一。

## 条件和完成反馈

- `g_route.junction`：十字连续两帧、左右连续三帧确认后的路口类型，十字优先。
- `g_route.junction_event`：新路口事件，只保持一帧；连续三帧无路口才重新允许触发。
- `g_route.line_found`：是否至少有一路在线，连续三帧确认。
- `line_found_event` / `line_lost_event`：有线、无线状态变化，只保持一帧。
- `g_mode_fsm.turn_count`：完成转弯总数，比较前后值即可判断动作完成。
- `g_mode_fsm.state_frames`：当前动作已经执行的控制帧数，可用于上层时间条件。

单帧事件应在 10 ms 的 `Route_Tick()` 中处理，主循环低频读取可能漏掉事件。
IMU 模式也会更新这些灰度条件，但不会运行循迹 PID。例如在自定义 IMU 直行步骤中，
发现 `line_found_event` 后调用 `Car_Track()`；若需要“到目标黑线”而非任意通道有线，
应按实际传感器图案定义条件，不能把 `line_found` 当作定位结果。

未来路径搜索放在主循环先计算路线，Route 周期入口只执行已经确定的路线步骤。
目前不引入路线搜索算法、动态内存或 RTOS。

## 故障与验证

IMU 未就绪、当前读取失败或 yaw 非有限值时进入 `CAR_FAULT_IMU`；转弯在
7°容差内连续三帧才完成，300 帧未完成则进入 `CAR_FAULT_TURN_TIMEOUT`。
故障与停车均清 PID 并将两轮 PWM 置零，Route 不会自动恢复运动。
确认问题已排除后，显式发送新的 `Car_*` 动作重新尝试。
OLED 显示大模式、动作、目标、故障编号和动作帧数。

```powershell
# 宿主行为测试，产物放临时目录。
.\tests\motion\run_tests.ps1

# Keil 完整重编译，临时工程直接读取工作区源码，输出也放临时目录。
.\tests\motion\build_keil.ps1
```

软件测试与编译不能代替上车验证。当前 IMU 直行死区是 1°，基础 PWM 是 400；
本次项目框架不修改 PID、PWM 或方向约定。先架空轮子检查项目动作顺序，
再在已知位置验证入口识别、前移时间和交接位置。运行上述命令查看当前代码的验证结果。
